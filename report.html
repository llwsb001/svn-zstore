1. 要做的事与最终选型

目标是换掉 SVN 服务端的存储，不再用 FSFS 落盘，而把 revision 数据放到对象存储；Zig 负责写后端。

最终采用方案 2：Zig 实现一个可插拔的 svn_fs 后端模块，SVN 通过 DSO 加载它，模块内部用自写 S3 客户端（SigV4 签名 + libcurl）把目录树快照与文件内容写成对象。方案 3（Zig 写独立存储网关）未采用。

关键前提：subversion 必须用 --enable-runtime-module-search 配置，否则 SVN_USE_DSO 未定义，loader 直接报 Unknown FS type 'zstore'；模块文件名必须是 libsvn_fs_zstore-1.so.0（带 .0）。

2. 架构

svn / svnadmin / svnserve
        │  svn_fs_open2("zstore") → dlopen libsvn_fs_zstore-1.so.0
        ▼
src/fs.zig ─── fs 级 vtable（youngest_rev / revision_root / begin_txn / verify …）
src/backend.zig ─── root vtable 33 项 + txn 7 项 + changes-iterator + history + id
        │
        ├── src/store.zig  对象模型与编解码（HEAD / revs / trees / blobs / props）
        └── src/s3.zig     PUT / GET / EXISTS / DELETE，SigV4 + libcurl
                            │
                            ▼
                     S3 / MinIO（bucket: svn，path-style）

Zig 0.17 已移除 @cImport，C 互操作全部改走 zig translate-c：src/c.h 聚合 apr + svn 头，生成 svn_bindings.zig（7256 行）与 curl_bindings.zig（4001 行）。同时 Zig 0.17 的 std 变化很大（无 std.fs.cwd、ArrayList 变 unmanaged、无 bufPrintZ），所以本地文件 IO 走 libc / APR。

3. 桶内对象格式

<prefix>/format            zstore/1\n
<prefix>/HEAD              rev=<n>\nroot=<sha256>\n
<prefix>/revs/<n>          rev=/parent=/root=/props=      ← props 是 blob key
<prefix>/trees/<sha256>   目录树快照（内容寻址，天然去重）
<prefix>/blobs/<sha256>   文件内容、props 编码块
  • tree 编码："ZST" + ver(1) + count(u32 BE)；每条目 name kind(u8) size created_rev created_path props copyfrom_rev copyfrom_path key
  • props 编码：u32 BE count + (name,value)*，解码结果必须 NUL 结尾
  • HEAD 最后写：依赖"单写者"假设，多客户端并发提交目前没有 CAS 保护

4. 本轮主线：把读路径与 blame 修到全绿

被替换段之前 svn blame 挂在 rev_hunt.c:1695 (mainline_path_revisions->nelts > 0)。这轮从 gdb + 逐点打日志定位，连带修掉四个真实缺陷：

缺陷表现与真因修法
事务路径未归一化svnadmin load 后 trunk 空：编辑器回调给的是相对路径 trunk，树缓存键是 /trunk，目录对象从未被 flushnormPath 强制前导 /
changed paths 缺前导斜杠svn log -v 打出 M trunk 而非 M /trunk；路径定向 log 漏掉修改版本，进而让 ls -r1 URL/trunk 报 location 找不到从根 / 起拼路径 + NUL 结尾
node id 编码了 revision同一节点跨版本 id 不同 → rev_hunt 判定"无关对象"，历史定位中断id = path + 内容 key
node_relation 过严同路径内容不同被判 unrelated，rev_hunt 直接 break，旧版本位置全丢返回 common_ancestor
history_prev 过早终止比较 rev-1 的 key 不同就返回 null，history 链第一步就断，blame 只算出一行首次先把当前点返回一次，再走 copyfrom/前一个版本

修完之后 blame 输出逐行归属正确：1 user hello / 2 user more（第一行来自 r1，追加行来自 r2）。

6. 真实 S3 后端：RustFS 实测通过

RustFS 1.0.6（Rust 写的 S3 兼容对象存储，单二进制 378 MB）在本机实测：代码零改动，只改 db/zstore.conf 的 endpoint。它默认只支持 path-style 寻址，正好与我们的客户端一致。

项结果
import / co / ci通过
ls / log / blame通过（blame 逐行 1 hello / 2 more）
svnadmin verify通过
dump → load通过（trunk/a.txt b.txt）
svn://（svnserve）通过
桶内对象落地15 个对象；本地 db/ 只剩 4 个几字节小文件
重启 RustFS 后读旧仓库数据持久（moto 是内存态，重启即丢）
RUSTFS_VOLUMES=/tmp/rustfs-data RUSTFS_ADDRESS=":9100" \
RUSTFS_ACCESS_KEY="zstore" RUSTFS_SECRET_KEY="zstore" \
RUSTFS_CONSOLE_ENABLE=false ./rustfs server /tmp/rustfs-data

# db/zstore.conf
endpoint=http://127.0.0.1:9100
region=us-east-1
bucket=svn
access_key=zstore
secret_key=zstore
注意：默认凭据是 rustfsadmin/rustfsadmin，务必覆盖；控制台 9001、API 9000（本机与 moto 共存时用 9100）；客户端若走 virtual-hosted 风格需设 RUSTFS_SERVER_DOMAINS。

7. 复现步骤

cd svn-s3 && zig build            # 产出 zig-out/lib/libsvn_fs_zstore-1.so.0

# subversion trunk（关键开关）
./configure --prefix=$PWD/install --enable-runtime-module-search && make -j4

# 运行
SVN=/home/user/myproject/svn-zig
LP=$(find $SVN/subversion -maxdepth 2 -name .libs -type d | tr '\n' ':')
export LD_LIBRARY_PATH="$LP$PWD/zig-out/lib"
svnadmin create --fs-type=zstore /tmp/R
svn import -m r1 /tmp/imp3 file:///tmp/R
svn log -v file:///tmp/R
svn blame file:///tmp/R/trunk/a.txt

7. 尚未闭环 & 待决策

  • 真实 S3 选型：RustFS 1.0.6 已实测跑通（见第 6 节），可作为落地方案；MinIO 开源二进制 dl.min.io 已 410、SeaweedFS release zip 无效。若要上生产，还需评估 RustFS 的运维方式（进程托管、TLS、多盘/多节点）。
  • 并发提交原子性：现在依赖"HEAD 最后写 + 单写者"，没有 conditional PUT / CAS，多客户端同时提交可能丢更新。要补的话，用 S3 的 If-None-Match/版本号或引入轻量锁对象。
  • 锁 / hotcopy / recover / pack 未实现；锁一律返回 UNSUPPORTED，hotcopy 无对象层快照语义。
  • open_txn 未持久化：进程重启后未提交事务不可恢复（对 svnadmin load 等一次性流程无影响）。
  • 内部 txn prop 过滤：svn:txn-user-agent、svn:txn-client-compat-version 目前会写进 rev 记录与 dump 输出，语义上应过滤。
